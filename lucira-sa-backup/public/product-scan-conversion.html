DASHBOARD LOGIC & DEFINITIONS

  1. Walk-ins come from Walkin_marge, one row per store visit (checked directly: every row is already a distinct phone+date+store combination, so repeat rows are genuine repeat visits, not duplicates). Total Walk-ins = distinct customers (by phone; rows with no phone each count as their own visit). Visit events = raw row count, shown as a secondary figure.
  2. Scans come from Pos.estimation_item_scan, matched to a product via Live_inventory on item_id (checked directly: item_id, item_code and Full_sku are effectively 1:1, so this is already an exact-variant match — no separate size/metal collapsing risk). The scan table's own "sku" column is a different, unrelated id and is not used for matching.
  3. Sales come from marketing_sale, matched to a scanned product by Full_sku (the single matching field — change it in one place, SALE_MATCH_FIELD in productScanConversionService.js, if the SKU convention differs later).
  4. Classification: scanned & sold → Scanned & Sold; scanned & not sold → Scanned but Not Sold; in Live_inventory but never scanned → Not Scanned. A product sold only through a channel that never logs a scan (e.g. online) is still "Not Scanned" by this rule, as specified.
  5. "Customers who scanned" is not shown — Walkin_marge (phone) and estimation_item_scan (item_id, sparsely populated party_id) share no reliable common customer key, so a per-customer walk-in→scan link cannot be verified from this data.
  6. Scan Rate (top funnel) = Scan events ÷ Walk-ins × 100 — a store-level engagement measure, not a verified per-customer conversion. Scan-to-Sale % = Scanned & Sold products ÷ Scanned products × 100.
  7. In the Price Band / Category tables, "Scan Rate" means something more specific: Scanned ÷ Inventory for that band/category (i.e. the share of that segment's stock that has ever been scanned) — labelled the same as the spec but clarified via the (i) tooltip and the note under each table.
  8. Price Band reuses marketing_sale's own existing Price_Range buckets (confirmed directly against the data) rather than a new scheme, per "use the existing business definition if one exists". Category = Live_inventory's item_group_name. Metal = metal_name. Size = item_size_name.
  9. Ageing = today − Live_inventory.document_date (earliest stock-ledger unit on record for that item_id) — the only field on Live_inventory that represents when a unit entered stock.
  10. Store codes are canonicalised so the same physical store never appears twice under different labels: Live_inventory/estimation_item_scan resolve company_id via the same store map used elsewhere in this app; Walkin_marge's own "FCS" rows are folded into "HWI" (the code marketing_sale/Live_inventory already use for that store). Walkin_marge also contains an "Amazon" store_code (an online channel logged through the same event) — kept as its own filterable value rather than dropped.
  11. Every filter (Date, Store, Category, Price Band, SKU, Metal, Size) is applied client-side against one BigQuery-sourced payload fetched on load/refresh — nothing here is static or manually entered. A scanned or sold item with no current Live_inventory match (sold out / discontinued) is excluded once any Category/Price Band/Metal/Size/SKU filter is active, since its attributes can't be confirmed.
  12. Data refreshes every 15 minutes server-side, or click Refresh for the latest right away.
